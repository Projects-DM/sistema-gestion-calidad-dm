## OBJECTIVE
Definir el **contrato mínimo SaaS ↔ Runtime** necesario para que:

- **FORM_CREATED**
- **FORM_VERIFIED**

ingresen al Runtime de forma:

- determinista
- escalable
- replay-safe (al menos “parcialmente” para Sprint 23)
- desacoplada de Supabase
- compatible con Analytics y Scoring

sin involucrar todavía:

- Selection
- Recovery
- Provider Binding
- Dispatches

---

## FASE 1 — CONTRACT SURFACE VALIDATION

### Audit Layer — campo mínimo requerido
Según auditorías previas y estructura esperada de Audit Records, el mínimo superficial requerido es:

- `eventId`
- `eventType`
- `timestamp`
- `actorId`
- `correlationId`
- `payload`

### Validación contra entidades SaaS disponibles
Entidades identificadas en auditorías previas:

- `sgc_form_responses.id`
- `profiles.id`
- `sgc_audit_logs.id`
- `sgc_evidences.id`
- (relacionadas: `sgc_forms.id`, EAV `sgc_response_values.*`)

**Resultado (estado por campo):**
- `eventId`: **READY** (mejor candidato: `sgc_audit_logs.id`)
- `eventType`: **PARTIAL** (existe mapeo create/verify pero falta taxonomía estable contractual)
- `timestamp`: **READY** (existencia de `created_at` y/o `verified_at` y timestamps de audit)
- `actorId`: **READY** (mejor candidato: `profiles.id`, con relación a `created_by/modified_by`)
- `correlationId`: **READY** (mejor candidato: `sgc_form_responses.id`)
- `payload`: **PARTIAL** (payload existe, pero el EAV no es estable; requiere normalización conceptual por adapter)

## FASE 2 — CORRELATION STRATEGY AUDIT

### CorrelationId candidate
Candidatos disponibles:

- `sgc_form_responses.id` (respuesta persiste durante create→verify)
- `sgc_audit_logs.id` (no persiste como “thread” entre eventos)
- `sgc_forms.id` (no es granular suficiente)

✅ Mejor candidata:
- `correlationId = response_id = sgc_form_responses.id`

**Clasificación:**
- **READY** para determinismo básico y conexión entre FORM_CREATED y FORM_VERIFIED.

---

## FASE 3 — EVENT IDENTITY AUDIT

### eventId (único, inmutable, persistente)
Candidato principal:
- `eventId = audit_log_id = sgc_audit_logs.id`

**Clasificación:**
- **READY**

## FASE 4 — ACTOR IDENTITY AUDIT

### actorId canónico
Candidatos:
- `profiles.id`
- `auth.user.id` (en Supabase)

Dado que se alinean en el SaaS (perfiles y auth), el contrato runtime debe usar el id persistente del actor:

✅ Recomendación:
- `actorId = profiles.id`

**Clasificación:**
- **READY**

---

## FASE 5 — EVENT TAXONOMY AUDIT

### Problema actual
En SaaS existe `sgc_audit_logs.action_type`:
- `create`
- `verify`

Pero el Runtime necesita `eventType` estable y desacoplado de nombres de dominio.

### Taxonomía objetivo
- `FORM_CREATED`
- `FORM_VERIFIED`

**Clasificación:**
- **PARTIAL**  
Existe la señal (create/verify), pero **no está contractualmente “curada”** a una taxonomía runtime estable.

---

## FASE 6 — PAYLOAD STABILITY AUDIT

### Payloads disponibles (por dominio SaaS)
- `FORM_CREATED` y `FORM_VERIFIED` tienen acceso conceptual a:
  - `form_id`
  - `response_id`
  - `values` (EAV)
  - evidences
  - `created_by`
  - `created_at`
  - (y para verify: `verified_at`)

### Riesgo detectado
- `sgc_response_values` (EAV) es flexible, pero no estable como payload runtime.
- Runtime necesita payload determinista para analytics/scoring y replay.

### Conclusión
No es apto consumir EAV “raw” en Runtime.

✅ Estrategia mínima conceptual:
- `payload` debe ser normalizado por un adapter hacia una estructura determinista (no implementada en esta fase).

**Clasificación:**
- **PARTIAL**

---

## FASE 7 — REPLAY SAFETY AUDIT

Secuencia:
- `FORM_CREATED` → `FORM_VERIFIED`

### Reconstrucción posible
Sí, porque existe identidad y timestamps:
- `audit_log_id`
- `response_id`
- `created_at`
- `verified_at`

### Falta para replay completo/recovery
No existen (en la forma actual del dominio SaaS) conceptos como:
- `event_sequence`
- `version`
- `replay_marker`

**Clasificación:**
- **PARTIAL** para Sprint 23
- **INSUFICIENTE** para Recovery

---

## FASE 8 — RUNTIME LAYER READINESS

Clasificación por capa, bajo integración mínima (solo FORM_CREATED/FORM_VERIFIED):

- **Audit Layer:** READY
  - porque se puede producir un record mínimo con los campos requeridos.

- **Analytics Layer:** READY
  - porque métricas básicas dependen de existencia/estado de eventos (con payload mínimo).

- **Scoring Layer:** PARTIAL
  - porque señales requeridas (aprobación/tiempo/evidencia) se derivan parcialmente; payload normalizado aún es “PARTIAL”.

- **Decision Layer:** NOT READY
  - requiere policy inputs y criterios; no está cubierto por contrato mínimo sin payload determinista de decisión.

- **Selection Layer:** NOT READY
  - requiere candidate executions/provider-independent selection payload.

- **Recovery Layer:** NOT READY
  - requiere replay-safe executions (marcado/versionado faltante).

## FASE 10 — EXECUTIVE REPORT

### A) Runtime Contract Surface
- Mandatory:
  - `eventId`, `eventType`, `timestamp`, `actorId`, `correlationId`, `payload`
- No obligatorio todavía:
  - `providerId`, `executionId`, `recoveryId`, `selectionId`, `selectionResult`

### B) Identity Strategy
- `correlationId = sgc_form_responses.id`
- `eventId = sgc_audit_logs.id`
- `actorId = profiles.id`

### C) Event Strategy
- `eventType` runtime debe ser:
  - `FORM_CREATED`
  - `FORM_VERIFIED`
- Mapeo existente: `action_type in {create, verify}` → taxonomy runtime (contrato por adapter)

### D) Payload Strategy
- Runtime NO debe consumir EAV raw.
- `payload` debe ser normalizado deterministamente (adapter conceptual).

### E) Replay Strategy
- Replay reconstructible parcialmente para Sprint 23 (create→verify).
- Recovery/Marcadores faltantes ⇒ NO READY para Recovery.

### F) Runtime Layer Readiness
- Audit: READY
- Analytics: READY
- Scoring: PARTIAL
- Decision: NOT READY
- Selection: NOT READY
- Recovery: NOT READY

### G) Sprint 23 Readiness
**Veredicto: SPRINT 23 APPROVED WITH LIMITED SCOPE**
- Alcance mínimo recomendado:
  - FORM_CREATED → Audit → Analytics
  - FORM_VERIFIED → Audit → Analytics
  - Scoring señales básicas derivadas (sin Decision/Selection/Recovery)

**Clasificación final T2.4: PARTIAL**
