## Contexto validado
- Runtime es un **Provider Execution Runtime**.
- Audit/Analytics existen y consumen a través del camino de ejecución/persistence routing.
- No existe Business Event Layer nativa para `FORM_CREATED` / `FORM_VERIFIED`.

---

## FASE 1 — RUNTIME ENTRY SURFACE INVENTORY (src/runtime/**)

Las superficies de entrada reales relacionadas con ingestión/registro son:

### 1) `PersistenceExecutionRouter` (runtime persistence routing)
- Responsabilidad: invocar persistencia del provider activo y, si existe `auditRecorder`, registrar `started/succeeded/failed`.
- Consumidores posteriores: `RuntimeExecutionAuditRecorder` → `RuntimeExecutionAuditRegistry` → `RuntimeProviderAnalyticsEngine`.
- Dependencias: `ActivePersistenceProviderManager`.
- Compatibilidad con eventos de negocio: **compatibilidad indirecta** (registra “operationType” de persistencia, no taxonomy business).

### 2) `RuntimeExecutionAuditRecorder` (audit record entry)
- Responsabilidad: crear/guardar audit records con `providerId`, `operationType`, `correlationId?`, etc.
- Consumidores posteriores: Analytics engine lee desde `RuntimeExecutionAuditRegistry`.
- Compatibilidad con eventos de negocio: permite `correlationId`, pero no acepta un envelope business `eventType/eventId/actorId/payload` de forma nativa.

### 3) `RuntimeExecutionAuditRegistry` (audit data index)
- Responsabilidad: almacenar records y servirlos por providerId.
- Compatibilidad: requiere que exista un audit record previamente escrito por el recorder.

### 4) `InMemorySaveLifecycleEventDispatcher` (transaction lifecycle eventing)
- Responsabilidad: despachar `SaveLifecycleEvent` (stages) in-memory.
- Limitación para Sprint 23: no modela taxonomía business `FORM_CREATED/FORM_VERIFIED` y es lifecycle/transaction-based.

### 5) Transaction Layer / Save Orchestrator
- Responsabilidad: orquestar submit/verify/evidence lifecycle.
- Limitación para Business Events: su modelo es transaccional (`TransactionKind`, `SaveLifecycleStage`) y no business events en primera clase.

## FASE 2 — ENTRY COMPATIBILITY MATRIX (opciones)

### Opción A — Integration Layer → `RuntimeExecutionAuditRecorder`
- Estado: **PARTIAL**
- Justificación (evidencia runtime):
  - El recorder permite `correlationId` opcional.
  - Pero no existe un contrato donde `eventId/eventType/actorId/payload` entren como parámetros directos: el recorder registra `providerId` + `operationType` + IDs opcionales.

### Opción B — Integration Layer → `PersistenceExecutionRouter`
- Estado: **PARTIAL**
- Justificación:
  - El router es el camino real donde se escribe audit cuando hay persistence execution.
  - Aun así, el audit `operationType` es derivado del flujo de persistencia (submit/saveDraft/loadDraft), no de `FORM_CREATED/FORM_VERIFIED` como taxonomy business.

### Opción C — Integration Layer → `SaveLifecycleEventDispatcher`
- Estado: **BLOCKED**
- Justificación:
  - `SaveLifecycleEventDispatcher` despacha `SaveLifecycleEvent` (stages) ligados a `transactionId/correlationId`, no `eventType` business `FORM_*`.

### Opción D — Integration Layer → Transaction Layer
- Estado: **BLOCKED / PARTIAL (insuficiente)**
- Justificación:
  - La transaction layer trabaja con `TransactionKind` (`submit/verify/workflow/...`) y produce lifecycle stages.
  - Para que eso sea `FORM_CREATED/FORM_VERIFIED` como business events requeriría que el runtime interpretara esos kinds como taxonomy business (no evidenciado como existente).

### Opción E — Integration Layer → Nueva Runtime Event Surface (conceptual)
- Estado: **BLOCKED** (por restricción de no modificar arquitectura)
- Justificación:
  - La fase pide identificar una superficie real existente; una “nueva event surface” implica cambios.

---

## FASE 3 — BOUNDARY VALIDATION (selección)

La opción que preserva mejor la arquitectura congelada (sin romper provider-factory):
- Evita acoplamiento Supabase dentro del runtime.
- Evita modificar Audit Core/Analytics Core.
- Minimiza cambios: usa el mecanismo existente donde audit escribe y analytics lee.

**Recomendación de entrada conceptual para Sprint 23:**
- **Opción B (Integration Layer → PersistenceExecutionRouter)** como superficie de entrada real,
- con traducción conceptual previa para que el audit/analytics use `correlationId` y métricas consistentes.

---

## FASE 4 — PIPELINE COMPATIBILITY (Audit → Analytics → Scoring)

- Cualquier ruta elegida debe terminar en:
  - Audit recorder escribe records en registry
  - Analytics engine lee registry y computa snapshots
  - Scoring consume snapshots

La ruta real existente que garantiza el pipeline es:
- `PersistenceExecutionRouter` (si hay auditRecorder) → `RuntimeExecutionAuditRegistry` → `RuntimeProviderAnalyticsEngine`.

Por ello, **aunque la taxonomía business no sea nativa**, esta es la superficie donde el pipeline “se vuelve ejecutable” sin cambiar core.

---

## FASE 5 — IMPACT ANALYSIS

### Impacto en Runtime
- Opción B: **medio**
  - porque requiere que la capa de integración traduzca taxonomy business hacia el modelo de audit existente (operationType/correlationId).

### Impacto en SaaS
- Opción B: **bajo-medio**
  - no requiere nuevas tablas; reutiliza `sgc_audit_logs` y `sgc_form_responses` para IDs.

### Riesgo arquitectónico
- **medio**
  - por incompatibilidad parcial entre taxonomy business y campos audit core.

---

## FASE 6 — EXECUTIVE DECISION (una recomendación)

1) Punto de entrada arquitectónicamente correcto (existente):
- **PersistenceExecutionRouter** (Opción B)

2) Opción a descartar:
- Opción C (SaveLifecycleEventDispatcher) y Opción D (Transaction Layer) como “entry” directo para business events taxonómicos `FORM_*`.

3) Preserva mejor la arquitectura congelada:
- Opción B minimiza cambios y respeta el core de Audit/Analytics.

4) Minimiza cambios futuros:
- porque se apoya en el camino real de audit/analytics ya operativo.

5) Habilita Sprint 23:
- **PARTIAL**: habilita el pipeline Audit→Analytics, pero la taxonomía business como first-class sigue siendo un objetivo parcial.

---

## RESULTADO
**Recomendación única (sin implementación):**
- Entrar por **PersistenceExecutionRouter** vía la Business Event Integration Layer, aprovechando `correlationId` derivable.
