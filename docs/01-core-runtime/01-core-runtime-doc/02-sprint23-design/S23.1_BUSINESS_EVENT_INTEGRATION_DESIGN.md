## CONTEXTO (consolidado)

- El Runtime actual es un **Provider Execution Runtime**.
- Audit y Analytics funcionan.
- No existe una **Business Event Layer** nativa.
- Los primeros eventos de negocio a integrar son:
  - **FORM_CREATED**
  - **FORM_VERIFIED**

Objetivo de Sprint 23:
- Integrar **Formularios Dinámicos** al pipeline **Audit → Analytics**.

---

## OBJETIVO

Diseñar conceptualmente la **Business Event Integration Layer** que permita:

SaaS
↓
FORM_CREATED / FORM_VERIFIED
↓
Runtime Audit
↓
Runtime Analytics
↓
Runtime Scoring (señales mínimas)

Sin modificar:
- Provider Factory
- Audit Core
- Analytics Core
- Scoring Core

---

## FASE 1 — BUSINESS EVENT ORIGIN ANALYSIS

### FORM_CREATED
- **Dónde nace (SaaS):** Dominio de Formularios Dinámicos, durante el “submit/create” de una respuesta.
- **Componente SaaS productor (evidencia):** `dynamicService.submitFormResponse(...)`.
- **Información típica del evento (fuentes SaaS auditadas):**
  - `sgc_form_responses.id` (responseId)
  - `profiles.id` (actor)
  - `sgc_audit_logs` con `action_type='create'`
  - (payload no debe ser EAV raw)

### FORM_VERIFIED
- **Dónde nace (SaaS):** Dominio de Formularios Dinámicos, durante el flujo de verificación.
- **Componente SaaS productor (evidencia):** `dynamicService.verifyFormResponse(...)`.
- **Información típica del evento (fuentes SaaS auditadas):**
  - `sgc_form_responses.id` (responseId)
  - `profiles.id` (actor)
  - `sgc_audit_logs` con `action_type='verify'`
  - `verified_at/status` (para señales de scoring)
  - (payload no debe ser EAV raw)

---

## FASE 2 — EVENT OWNERSHIP (Ownership Matrix)

### Datos y quién los produce

| Campo | Propietario recomendado | Justificación (evidencia consolidada) |
|---|---|---|
| actorId | **SaaS** | Alineado con `profiles.id` (aprobado en estrategia de identidad). |
| eventId | **SaaS** | Mejor candidato: `sgc_audit_logs.id` (persistente). |
| correlationId | **SaaS** | Mejor candidato: `sgc_form_responses.id` (hilo create→verify). |
| timestamp | **Runtime o SaaS (según contrato mínimo)** | En el contrato mínimo validado existe timestamp requerido; el runtime puede setear internamente si el core lo hace, pero el diseño debe asumir consistencia. |
| payload | **SaaS (normalizado conceptual)** | Payload no debe consumir EAV raw; debe ser determinista y desacoplado de estructura EAV. |

---

## FASE 3 — INTEGRATION BOUNDARY

### Frontera arquitectónica correcta

**Termina el SaaS:**
- dominio de formularios, decisiones humanas de verificación
- persistencia en `sgc_*`
- producción de señales de audit (`sgc_audit_logs` create/verify)

**Comienza la Business Event Integration Layer:**
- traducción/curación conceptual de:
  - `create` → `FORM_CREATED`
  - `verify` → `FORM_VERIFIED`
- construcción de un **evento mínimo** consistente (sin EAV raw)

**Comienza el Runtime:**
- recepción del evento traducido dentro del pipeline existente **Audit → Analytics**.

---

## FASE 4 — TRANSLATION LAYER DESIGN (create/verify → FORM_*)

### Objetivo
Transformar señales del SaaS:
- `action_type='create'` → `FORM_CREATED`
- `action_type='verify'` → `FORM_VERIFIED`

### Protección de pureza (reglas de frontera)
La capa de integración:
- **No expone tablas Supabase**
- **No usa EAV raw como payload**
- **No acopla Runtime a supabase**

### Contrato conceptual mínimo que debe producir
- `eventId` (sgc_audit_logs.id)
- `eventType` (FORM_CREATED / FORM_VERIFIED)
- `timestamp`
- `actorId` (profiles.id)
- `correlationId` (sgc_form_responses.id)
- `payload` normalizado determinista

---

## FASE 5 — AUDIT ENTRY DESIGN

### Primer consumidor runtime
El diseño debe entrar por el primer mecanismo de registro existente:
- Runtime Audit es alimentado por el mecanismo de auditoría existente (audit core).

**Nota de diseño (sin implementación):**
- El Runtime audit core actual registra ejecuciones usando su estructura de audit.
- La Business Event Integration Layer debe producir una traducción compatible con esa estructura, manteniendo el contrato mínimo validado para Sprint 23.

---

## FASE 6 — ANALYTICS FLOW DESIGN

### Flujo esperado
Runtime Audit (registra eventos mínimos)
→ Runtime Analytics (deriva métricas básicas)

### Métricas objetivo de Sprint 23
- conteos por tipo (FORM_CREATED / FORM_VERIFIED)
- señales básicas para scoring (completado/verificado/latencia aproximada)

---

## FASE 7 — SCORING READINESS (señales mínimas)

Señales disponibles post-integración (conceptuales):
- `verification_latency` (tiempo create→verify, si el diseño conserva timestamps suficientes)
- `evidence_presence` (solo si el payload/normalización incluye una señal derivable)
- estado verificado vs no verificado

Estado esperado:
- Scoring: **limitado / PARTIAL** (según evidencias de contrato mínimo).

---

## FASE 8 — PROTECTION RULES (congelar core)

No se requiere modificar:
- Provider Factory
- Audit core
- Analytics core
- Scoring core

La integración debe preservarse como:
- traducción conceptual en una capa dedicada
- sin romper provider-agnostic runtime

## FASE 10 — EXECUTIVE DECISION (Sprint 23)

1) ¿La Business Event Integration Layer es suficiente para Sprint 23?
- **Sí con alcance limitado:** se integra FORM_CREATED y FORM_VERIFIED para habilitar Audit → Analytics.

2) ¿Permite integrar FORM_CREATED y FORM_VERIFIED sin romper el Runtime?
- **Sí, a nivel arquitectura conceptual**, siempre que el evento traducido respete el contrato mínimo de Sprint 23 (sin EAV raw) y sea compatible con el mecanismo actual del Audit core.

3) ¿Qué componentes se implementan primero en Sprint 23? (solo plan conceptual)
- capa de traducción Taxonomy + Identity + payload mínimo normalizado
- canal de entrada hacia Audit
- validación de Analytics consumption

4) Ruta crítica
- Identity + Taxonomy + Payload normalizado mínimo → Audit ingestion → Analytics derivados

Diseño conceptual completo de la Business Event Integration Layer para Sprint 23.

Sin implementación.
Sin cambios productivos.
