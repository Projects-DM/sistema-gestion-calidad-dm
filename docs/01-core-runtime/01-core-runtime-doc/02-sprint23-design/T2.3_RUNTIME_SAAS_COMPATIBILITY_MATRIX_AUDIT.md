> Nota: En esta auditoría SOLO se evalúa compatibilidad conceptual y de contratos, no se realizan cambios.

## FASE 1 — Contract Compatibility Matrix

| Runtime Contract / Expectation | SaaS Source | Compatibility |
|---|---|---|
| **Audit Contract** (runtime ingestible por Audit Layer) | `sgc_audit_logs` (dynamicService escribe create/verify) | **READY** (existe auditoría persistente con actor+timestamp+payload parcial). **Limitación:** falta convención explícita de correlation/transaction IDs y tipos event→audit.
| **Analytics Input** (runtime analytics derivable de audit stream) | `sgc_audit_logs` + `sgc_form_responses` + `sgc_evidences` | **PARTIAL** (se pueden derivar métricas simples; para determinismo completo se requiere normalización de eventos y correlación estable).
| **Scoring Input** (scoring requiere señales consistentes: éxito/fallo/latencia/volumen) | `sgc_form_responses.status`, `sgc_audit_logs.action_type`, `sgc_evidences` | **PARTIAL** (se puede score operativo; para scoring tipo “provider execution” falta mapping a ejecución runtime y duración/éxito determinista por correlación).
| **Decision Input** (decision requiere workflow estados/razones) | verify workflow: `status` approve/reject + `verification_comment` | **PARTIAL** (existe estado y decisión humana; automatización runtime requiere un contrato de “policy input” y reglas/criterios).
| **Selection Input** (selection requiere payload provider-agnostic y elección determinista) | provider-agnostic payload NO existe en SaaS | **NOT_READY** (SaaS no tiene selección de providers ni payload de ejecución; runtime selection no aporta sin adapters/event contract que representen “ejecución candidata”).
| **Recovery Input** (retry/replay capaz) | retry del SaaS no modelado como event-sourced retries | **NOT_READY / BLOCKED** (SaaS no presenta un modelo de replays deterministas; si se hace mapping directo se requiere estrategia de idempotencia y replay-safe event identity).

## FASE 2 — Identity Compatibility Audit

Runtime requiere (conceptualmente):
- `correlationId`
- `transactionId`
- `executionId` (si aplica)
- `recoveryId`

SaaS actualmente ofrece (evidencia):
- `user.id` (Supabase Auth + `profiles.id`)
- `sgc_form_responses.id` (responseId)
- `sgc_form_responses.form_id`
- `sgc_audit_logs.response_id`, `modified_by`, `created_at`
- `sgc_evidences.response_id`

**Evaluación por identidad**
- `response_id` → posible `correlationId` (estable por entidad)
  - **Replay-safe:** PARTIAL (si hay reintentos/no idempotencia, puede duplicarse)
  - **Determinism:** PARTIAL (depende de mapping consistente create/verify)

- `form_id` → no es suficiente para correlación de ejecución

- `evidence_id` → útil para signals, pero no para execution identity

**Resultado identidad:**
- **PARTIAL** global

## FASE 3 — Event Compatibility Audit

### FORM_CREATED
- SaaS: `dynamicService.submitFormResponse()` escribe `sgc_form_responses` y `sgc_audit_logs(action_type='create')`.
- ¿Puede transformarse a Runtime Event?
  - **READY** (hay suficientes campos: actor, timestamp, payload parcial)
  - **Limitación:** event identity/duration y mapping determinista a transaction/execution no está contractualmente definido.

### FORM_VERIFIED
- SaaS: `dynamicService.verifyFormResponse()` actualiza status/verified fields y agrega `sgc_audit_logs(action_type='verify')`.
- ¿Puede transformarse?
  - **READY/PARTIAL** (hay evento con actor+timestamp+payload; falta link determinista a “transaction execution” si runtime lo requiere).

### EVIDENCE_ADDED
- SaaS: `submitFormResponse` inserta `sgc_evidences` pero NO inserta `sgc_audit_logs` específico para evidencias.
- ¿Existe como evento?
  - **PARTIAL**: se puede inferir por existencia de `sgc_evidences`, pero no como evento audit del pipeline.

### DISPATCH_IMPORTED / DISPATCH_UPDATED
- SaaS: despachos CRUD en `despachos`.
- ¿Existe evento/audit persistente?
  - **BLOCKED/NOT_READY** (no hay equivalente a `sgc_audit_logs` para despachos).

## FASE 4 — Runtime Purity Audit
Verificación de que la integración futura NO introduzca acoplamientos prohibidos:
- **No insertar Supabase dentro del Runtime**: vía adapters fuera del runtime.
- **No introducir entidades SaaS en Runtime**: runtime recibe eventos normalizados.
- **No introducir lógica UI en runtime**: runtime solo interpreta contratos.

**Riesgo:**
- **PARTIAL** (si el diseño propuesto usa “lectura directa SaaS tables” desde runtime, rompería pureza). La estrategia correcta es: Runtime consume **eventos/adapters ya normalizados**, no queries.

---

## FASE 5 — Adapter Sufficiency Audit

Evaluación:

- **AuditLogAdapter**: `sgc_audit_logs → Runtime audit records`
  - **Suficiente:** Sí para Audit Layer.

- **IdentityAdapter**: map `response_id`/`user_id` → correlation/transaction/recovery ids
  - **Insuficiente:** parcialmente. Falta definir strategy de idempotencia y replay identity.

- **FormResponseAdapter**: `sgc_form_responses` → inputs (status/verified_at)
  - **Suficiente:** para analytics/scoring operativos.

- **EvidenceAdapter**: `sgc_evidences` → evidence signals
  - **Insuficiente** como evento audit: no hay `sgc_audit_logs` por evidencia; solo se infiere.

- **DispatchAdapter**: `despachos` → runtime events
  - **Faltante/Insuficiente:** bloqueado (no hay audit/event contract persistente).

**Resultado adapter sufficiency:**
- **PARTIAL** global
